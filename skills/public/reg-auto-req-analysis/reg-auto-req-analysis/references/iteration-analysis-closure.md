# 证据驱动的存量产品迭代分析闭环

用于阶段二生成变更方案。先还原既有产品，再判断本次迭代的业务价值和改动边界；不把代码图谱候选、技术定位或未确认信息写成业务事实。

## 闭环顺序

1. **现状基线**：确认用户与场景、当前行为或规则、既有边界。先把原始描述中的每个入口、触发阶段（加载/选择/保存/打印等）、条件和期望动作列成内部场景矩阵；每个场景必须在方案或非目标中有唯一落点，不得把不同触发点泛化为同一“保存时处理”。涉及状态机、频次、库存/记账、医保或历史数据时，矩阵至少含“对象状态 × 触发事件 × 已处理状态 × 期望动作 × 验收结果”，覆盖新增、修改、撤销/停用、重复、部分完成和失败重试。界面呈现调整还须核实当前页与同类页面的状态标识、颜色、图标和位置规则；仅定位组件不等于证实设计规则。仅使用工作项、已解析附件、已证实的产品知识或已核实页面；在 v2 计划的 `evidence_refs` 中逐章节引用 `work-item`、`req:<索引>`、`kb:<索引>` 或 `wiki:<索引>`，其中 `req:` 只证明历史工作项事实，技术证据不进正文。**界面/布局类需求**（增减展示字段或列、布局调整、界面交互）的现状 UI 事实（当前界面有哪些字段/区域/交互、没有什么）须由至少两源交叉证实：wiki 界面布局描述（或 Raw）、受控页面观察/可追溯截图、代码图谱证实的页面结构——**工作项描述对当前 UI 的叙述不充当独立证据源**（需求方可能对现状记忆不准）；wiki 覆盖该模块时为必需源之一，未覆盖记 `evidence_gap`（"界面现状缺 wiki 交叉证实"），AUTO-ANA 候选降为 MANUAL-REVIEW。
2. **问题与目标**：说明触发条件、业务影响、根因判断和本次目标。性能/异常需求必须判断方案是否直指根因；使用层规避按 QC 规则回退 `NEED-REVIEW`。**痛点真实性核对与需求方方案合理性评估（必做·先于差异与范围落笔）**：①**痛点核对**——需求方所述痛点/现象须与现状基线交叉对照，若痛点称"看不到/没有 X"而现状基线（经交叉证实）表明 X 已在某处展示或已有该能力，标记"痛点与现状不一致"；②**合理性与必要性评估**——基于现状基线与痛点核对，对每个需求点判断是否合理（需求方方案是否与现状冲突）、是否必要（问题是否已由现状覆盖，含同界面或相邻界面是否已展示同字段）、是否有更优解（信息层级更合理、改动更小的替代）；合理则沿用需求方方案；不合理/不必要/有更优解时，**按层级二分分流，不得降级**：**①方向/位置/范围存疑**——需求方方案的位置或方向与现状合理性冲突（如"信息应在 A 处展示却要求放 B 处"、与既有现状重复冗余、整体改动方向偏了），**回退 `NEED-REVIEW`**（产品确认方向，不在分析里擅自改方向）；**②方向 OK、仅实现细节存疑**（取数口径/多记录聚合/文案/格式），优化方案并简述理由，形成 `analysis_gap`（PM 确认细节）+ 终局 `MANUAL-REVIEW`。**不得把方向性问题降级为细节 gap**（如把"应放右却要求放左"当成"左侧怎么聚合"的口径问题处理）；**不评估而直接照搬需求方方案属流程违规**。
3. **差异与范围**：逐项写现状、目标状态、保持不变项和受影响触点。未知的正确性类范围、取数口径或权限边界不得默认“按现有逻辑”。
4. **方案取舍**：写推荐方案、替代方案或“不适用”及选择理由。只有一个显然可行方案时，替代方案写“不适用：<原因>”；不得用候选实现替代方案结论。方案含跨分页排序、全量加载、批量加载、弹窗选择、异步或跨页面联动时，先验证数据获取层、排序/过滤层、组件能力和用户实际触发时机；验证不足时保持候选并走人工复核。
5. **成功衡量与非目标**：优先写可量化指标；纯展示类小改动可写可观察的业务验收结果。所有需求都要写明确非目标，防止范围蔓延。
6. **范围—方案—验收追踪**：在变更方案中按改动点逐行写“范围/改动点 → 方案/目标行为 → 验收场景与结果”，三列均不可为空；每行标为“已证实 / 合理假设 / 待业务确认”。合理假设仅限呈现类默认，写明适用边界；待业务确认必须一对一关联 `analysis-gap:<id>`，不得用技术定位缺口代替。
7. **类别化交付**：按 `analysis-description-writing-rules.md` 生成受控“分析者描述”，仅写按类别裁剪后的业务结论；公共摘要、证据、追踪项、风险和验收保留在变更方案其它章节，且必须能追溯到前五步结论。

## 缺口路由

| 缺口 | 处理 |
|---|---|
| 需求方向、根因、业务范围、取数口径、权限口径不清 | 回退阶段一 `NEED-REVIEW`；由产品或研发负责人补充后重新触发。 |
| 需求方方案的方向/位置/范围与现状合理性冲突（如应在 A 处展示却要求放 B 处、与既有现状重复冗余、整体方向偏了）/ 痛点与现状不一致 | 回退阶段一 `NEED-REVIEW`（产品确认方向），不在分析里擅自改方向 |
| 方向 OK，仅取数口径/多记录聚合/文案等实现细节存疑 | 经合理性评估优化方案并形成 `analysis_gap`（PM 确认细节），终局 MANUAL-REVIEW |
| 需求已清，但现有实现、相似能力或方案取舍无法证实 | `MANUAL-REVIEW`；在仅供审计的 `evidence_gaps` 指派研发或知识库治理补充证据，**不得**写入 PM 的 `analysis_gaps`。 |
| 界面方案未核实现有页面/同类页面设计规则，或字段异常仍有未追踪取值分支 | `MANUAL-REVIEW`；记录 `evidence_gaps`，不得按实施建议或单条命中证据自动放行。 |
| 格式、文案、顺序、空值展示等呈现细节缺失 | 按 `confidence-heuristic.md` 写合理默认和适用边界，不生成 gap。 |

## 输出边界

- 变更方案正文只写业务结论、业务路径、规则、范围和验收；不写仓库、类、方法、接口、Mapper 或表字段。
- `kb.findings` 保留证据状态、工具和技术定位；正文不暴露其细节。
- v2 `evidence-loop-v1` 计划必须含模板定义的闭环区、`evidence_refs` 和 `evidence_gaps`；AUTO 的现状基线、差异与范围、方案取舍必须引用 `kb.findings` 的已证实项。
- `analysis_gaps` 只保留 PM 可补齐的业务信息并生成 `manual-followup`；`evidence_gaps` 不生成附件、不写 TFS，只进入运行审计。
