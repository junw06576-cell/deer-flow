# 质控默认核对项 + 待补充清单模板

> 本文件给质控阶段提供：① 未被事前质控规则覆盖时的通用核对；② 内嵌于执行计划 JSON、由执行器物化上传的「待补充清单」（`checklist`）结构。
> 需求类型、PIMIS 优先级、期望日期、标题项目关键词与高风险早筛以 `config/qc-rules.md` 和 `pre-qc-rules.md` 为准；本文件不覆盖它们。

---

## 一、通用补充核对（事前质控后执行）

**第 0 步·先完成准入路由与事前质控**：先查 `config/qc-rules.md` 与 `pre-qc-rules.md`：纯联调排除、范围排除、时效、标题项目关键词和高风险早筛。命中 `SKIP-ANALYSIS` 时立即停止，不再生成问题；`NEED-INFO`、范围/时效/根因方向等硬阻断不进入分析。其它初判 `NEED-REVIEW` 必须先跑 `qc-kb-recipe.md` 的 KB/wiki 补证，再决定最终是否进入分析。

逐项判断，按下方映射出终局。**任一"否"且属核心信息缺失 → NEED-INFO；核心齐但有歧义/存疑 → NEED-REVIEW；全"是" → pass。**

| # | 核对项 | 判据 |
|---|---|---|
| 1 | 描述非空且可理解 | `description` 非空、非占位文字、能说清"要做什么" |
| 2 | 有验收标准/验收口径 | 能从描述或附件中识别"做完算什么"（口径、阈值、范围） |
| 3 | 涉及模块/接口/数据对象可识别 | 能看出改哪个模块、是否依赖接口/表；**缺接口文档等核心依据 → NEED-INFO**。触及判定面时按 `qc-kb-recipe.md` 发现链核对实体是否存在（命中写 `items`/`kb_note`，三态） |
| 4 | 合理性：无内部冲突 | 描述自身不前后矛盾 |
| 5 | 合理性：无明显重复 | 与已知功能/近期需求不显著重复——按 `qc-kb-recipe.md` 发现链检索（多组关键词 + 按状态过滤 + get_work_item 核验，见 `_lib/knowledge-base.md` §四）。命中须标 `maturity`：**实现级命中**（`maturity=已落地`）→ 写 `items` 请产品确认，经本维度参与终局；**若进一步判定其能力覆盖本次诉求（一套公版），分析阶段须按“功能已存在”判 MANUAL-REVIEW（见 `../config/analysis-rules.md` §判定优先级第 2 项）**；**描述级命中**（`maturity=设想`，仅描述提及解决设想）→ 只记背景线索，不作"已实现"依据；KB 未就绪则据工作项本身判断；**界面类需求（增减展示字段/列/布局）**还须核对"该信息是否已在同界面或相邻界面其它位置展示"——已有时标"界面冗余"请产品确认（选择式 item，依赖 KB/wiki 已读取） |
| 6 | 合理性：业务上说得通 | 符合常识与产品线业务，无反常识诉求 |
| 7 | **spec 清晰度：范围/边界** | 改动适用范围（全部/子集）、边界（含/不含）是否明确；不明且影响实现 → `NEED-REVIEW`（产品）。**存疑先按§二·收敛规则二分：呈现类→默认现状不变（notes）不产 item；正确性/方向类→item** |
| 8 | **spec 清晰度：取值/数据源** | 涉及取值/数据源时，是否给"**类别 + 口径/范围**"（只给类别不给口径/范围 → `NEED-REVIEW`；完全无数据源 → `NEED-INFO`）。**取值口径命中正确性关键词（金额/精度/结算等）才进 items；呈现类口径（列宽/排序/空值文案）默认现状不变记 notes** |
| 9 | **spec 清晰度：与现有路径一致性** | 与既有相似功能/路径是否冲突或需对齐；存疑 → `NEED-REVIEW`（产品）。**默认现状不变：未要求对齐即按现状，仅"对齐错了会资损/数据错/违规"才进 items** |
| 10 | **需求方向/根因一致性（治标警惕）** | 性能/异常抱怨（卡顿/慢/等待/超时/延迟/崩溃/卡死/无响应/数据错乱/报错）诉求的方案须针对根因优化（加索引/分页/异步/缓存/重构）；若方案为使用层规避（上限/提醒/分批/限制/阈值/不超过/最多N条/临时截断/规避/绕过）而非根因排查 → **方向类存疑** → `NEED-REVIEW`（产品 + 研发负责人）。**异常量级数据不应致异常卡顿/错误**：规避方案治标可能掩盖真实缺陷，须先确认是否排查根因 |

> **spec 清晰度的意义**：PASS 进分析的应是“spec 已清”，分析不应再抛 spec 类待确认。正确性/方向类存疑先初判 `NEED-REVIEW`；仅当 KB/wiki 的已证实现状能逐项回答、且无剩余缺口时才复核为 PASS。dev 级细节（具体字段名/mapper）不算 spec 歧义，不在 QC 判。

> **单次集中确认**：最终 PASS 前须按分析闭环做一次业务决策预演。范围、业务含义/取值、业务规则、权限、异常处置和验收中，只要存在 PM 可回答且答案会改变方案或验收的缺口，就在本阶段一次性合并提问。技术定位、代码路径和知识源覆盖不足不问 PM，转内部 `evidence_gaps`。

**终局映射（按优先级）：**
- **准入排除**（第 0 步）→ `SKIP-ANALYSIS`，不产 checklist；其它事前质控阻断按 `qc-rules.md` 的 `NEED-INFO` / `NEED-REVIEW` 与责任方处理
- 第 1/3 项为"否"（核心信息缺失）→ `NEED-INFO`；第 8 项"完全无数据源"→ `NEED-INFO`
- 第 2/4/5/6 项为"否"或存疑（齐但不清晰/存疑）→ `NEED-REVIEW`
- 第 7/8/9 项（spec 清晰度）存疑先按§二·收敛规则二分：**正确性/方向类**存疑 → `NEED-REVIEW`（产品），item 受 `MAX_QC_ITEMS` 收敛；**仅呈现类**存疑 → `pass`（呈现默认记 `notes`，若无其它 item 则不产清单）
- **第 10 项（需求方向/根因）命中 → `NEED-REVIEW`（产品 + 研发负责人），item `priority:P0`，受 `MAX_QC_ITEMS` 收敛（P0 永不降级）**
- 全"是" → `pass`

### KB/wiki 补证放行

初判 `NEED-REVIEW` 不直接生成计划。对每个初判 item，先用 `qc-kb-recipe.md` 查产品 wiki 与 KB：仅当已证实 finding 直接覆盖同一业务范围的规则/取值语义/既有路径，并且这些事实与本需求不冲突时，才可消除该 item。全部 item 被消除后复核为 `PASS`，阶段二计划必须带 `qc_evidence_resolution`；任一 item 仍是候选、未确认、只证明局部技术实体，或仍需产品选择新规则时，保留最终 `NEED-REVIEW` 并生成本节 checklist。`NEED-INFO`、时效/范围和 #10 根因方向不适用此放行。

## 二、`checklist` 字段（内嵌于执行计划 JSON，由执行器物化为 inline 附件上传）

> **不再生成独立 `.md`**。清单作为顶层 `checklist` 字段写进 `执行计划_<id>_<run_id>.json`；执行器物化为附件 `待补充信息_<id>_<run_id>.json` 上传 TFS，正文 = 运行标记行 + `checklist` 的 JSON。NEED-INFO 与 NEED-REVIEW 都用此结构，只改 `responsible` 与 `items`。

### 收敛规则（现有产品改动·问题生成上限与分流）

> 改现有产品时，需求没说到的「隐式默认」容易让 AI 把每个疑点都变成确认问题、导致清单发散。本规则用三个杠杆收敛：**默认规则**（该问 vs 该默认）+ **优先级**（保留谁）+ **上限**（留几个）。仅作用于 spec 清晰度疑点（#7/#8/#9）与其它「需求没说到」的疑点；**NEED-INFO 核心缺失（#1 描述、#3 模块/接口/数据对象、#8 完全无数据源）始终必问，不受本规则影响**。

**杠杆 1·默认规则（核心）**：现有产品改动 + 需求没说 → 默认**现状不变**。先按下表做呈现/正确性二分（正确性类关键词与分析 `../references/confidence-heuristic.md` 正确性类为**同一集合**，调整须同步）：

| 类别 | 范围 | 处理 |
|---|---|---|
| **呈现类** | 格式、文案、顺序、空值显示、颜色、布局、边界展示（错了只是体验） | 默认现状不变 → 写 `notes[]` 标注假设，**不进 `items`、不单独触发 NEED-REVIEW** |
| **正确性类** | 命中关键词之一即按正确性类（不得用呈现类默认兜）：**金额、精度、计算、舍入、医保、结算、扣减、回滚、退费、过账、阈值、上限、下限、累计、汇总** | 进 `items`（`priority:P0` 或 `P1`） |

> 仲裁：「错了会不会造成资损/数据错误/违规？」会 → 正确性类；不会 → 呈现类。拿不准按正确性类处理（保守）。

**杠杆 2·可调上限 `MAX_QC_ITEMS`（收敛系数）**：
- `MAX_QC_ITEMS = 5`（普通需求目标为 1–3 个业务决策主题；复杂需求最多 5 个；执行器会拒绝超过 5 项的计划；调参须同步 `pipeline.py`）。
- 候选 items（经杠杆 1 分流后）≤ 上限 → 全保留。
- \> 上限 → 先按范围、业务含义/取值、规则、权限/异常、验收五类决策面合并相近问题，再按杠杆 3 优先级保留 top-N；**P0 不得直接降为默认假设**。无法在 5 项内表达时用一条结构化聚合问题覆盖同一决策面；不得把仍会改变业务正确性的 P0 降级为 `notes`。

**杠杆 3·优先级分层（`priority` 字段）**：每个 item 带可选 `"priority": "P0" | "P1" | "P2"`（执行器不校验、原样进 TFS，供下游按优先级作答）：

| 档 | 含义 | 上限处理 |
|---|---|---|
| **P0** 阻断 | NEED-INFO 核心缺失 + 正确性类 spec 存疑（决定终局的主因）。≡ 原 `primary:true` | **永不降级** |
| **P1** 重要 | spec 方向性存疑但非正确性关键词、影响实现方向 | 超上限时降级 `notes` |
| **P2** 呈现 | 呈现类疑点 | 杠杆 1 已直接路由 `notes`，通常不作为 item |

> 兼容：`primary` 字段保留不动；新清单用 `priority`，`priority:P0` 即旧 `primary:true`（P0 项可同时置 `primary:true` 兼容旧下游，可选）。

**提问准入四问**：候选问题只有同时满足下列条件才可进入 `items`：①答案会改变实现或验收；②无法安全沿用已核实的现状；③工作项/附件确实未给出；④不能由产品现状或证据链直接回答。需求已明确限定“入库”“当前页面”“仅联调”等范围时，不得自行扩展到采购/调拨/退货、其它页面、监管闭环等未提及场景；外部文档未读取是证据限制，不自动转化为一组业务确认问题。

**重跑去重规则**：`items[].id` 是跨轮稳定业务决策 ID。新策略使用语义 ID（如 `q-scope`、`q-value-rule`、`q-permission-exception`、`q-acceptance`，必要时追加业务对象短名），禁止按本轮顺序重编 `q1/q2`。编排器传入的 `human_feedback.question_id` 命中该 ID 后，答案作为本轮已确认业务证据；除非当前 TFS revision/新附件与答案直接冲突，否则不得重复询问。未回答项保留原 ID，新发现项按决策面去重后追加。

  "verdict": "<NEED-INFO | NEED-REVIEW>",
  "tag": "<PM-AI-QC-NEED-INFO | PM-AI-QC-NEED-REVIEW>",
  "responsible": "<实施/创建者（NEED-INFO） | 产品/研发负责人/现场/排期方/非本组流程（NEED-REVIEW，按规则命中填写）>",
  "generated_at_utc": "<ts>",
  "items": [
    {
      "id": "q-scope",
      "priority": "P0",
      "category": "<可选：规则分类，如 高风险·支付结算(②) / 内容·描述可分析性>",
      "responsible": "<可选：该条具体责任方，与顶层不同时填>",
      "primary": false,
      "question": "<要补充的问题：一句话，问责任方要什么>",
      "why": "<可选：为什么质控判定需要它>",
      "options": ["<推荐可能存在的内容1>", "<推荐可能存在的内容2>"],
      "allow_other": true
    }
  ],
  "notes": ["<可选：非阻断提示，如标题归属建议补全>"],
  "passed": ["<可选：已通过项，如 范围/时效/归属 的核对结论>"],
  "kb_note": "<可选：KB 发现链三态摘要，列命名实体——如 '图谱事实: DischargedSettlementController.saveSettlement(query); his组合项目明细$(get_table_knowledge,Excel对照表) | 推断: 校验落 saveSettlement 链路 | 未确认: 费用明细/结算源表(DB 无命中)'>",

### 填写规范
- **逐条对应**默认核对项（或规则命中的项）里判为"否"的那几条，**禁止编造**没核到的缺失项。命中项**先经§二·收敛规则分流**：呈现类→`notes`、正确性/方向类→`items`；`items` 受 `MAX_QC_ITEMS` 收敛，不止第一项。
- `items[].question` 必须是**责任方可直接回答的问题**；`options` 列出**推荐的可能答案/口径**（选择式，2~5 条为宜），`allow_other:true` 表示允许自由补充——这是为下游对接（TFS-BUDDY/DeerFlow/责任方）**直接提取"要补什么 + 推荐可能情况"**而设。
- 责任方必须明确：`NEED-INFO` → 实施/创建者；`NEED-REVIEW` → 按 `qc-rules.md` 的命中规则指定产品、研发负责人、现场、排期方或非本组流程。
- `priority` 三档（P0 阻断 / P1 重要 / P2 呈现）见§二·收敛规则杠杆 3；P0 即原 `primary:true` 的主因条目，P0 项可同时置 `primary:true` 兼容旧下游。
- **KB 发现可作 `items`**：按 `qc-kb-recipe.md` 跑发现链命中的命名实体（含疑似重复/已实现），可写成选择式问题（三态标注放 `why`），经现有维度（#3/#5）参与终局——**不新增 verdict、不加 KB 专属规则**。命名实体示例："校验加在 `DischargedSettlementController.saveSettlement` 链路？"（图谱事实：控制器存在；插入点 推断）。
- 语言简洁、可执行；运行标记 `<!-- auto-req-run:<run_id> -->` 由执行器物化时注入，**不要手写进 `checklist`**。
