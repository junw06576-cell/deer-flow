# 分析者描述书写规则

用于 `change-plan` 的“分析者描述”区。先从工作项及已解析附件选择一项或多项类别；只选有证据支撑的类别，类别可组合。计划中以相同 ID 写入 `analysis_description.categories`。

> **权威参考**：按类别区分的书写规范、优质示例与写作要点源自仓库根 `需求分析方法.md`「分析者描述书写规范」；本文件将其落地为本 skill 的受控格式。类别清单与必需维度是代码侧硬约束的镜像（见 `../_lib/tfs/pipeline.py` `ANALYSIS_DESCRIPTION_REQUIREMENTS`），二者必须逐字段一致。

## 一、总则

- 精准优先：简单事项用最少句子说清楚；复杂、跨模块或跨系统事项才展开。
- **闭环先行**：先按 `iteration-analysis-closure.md` 写明现状、目标状态、保持不变项、方案取舍、成功衡量和非目标，再选择类别并填写本区。类别、变更点、风险和验收必须与闭环结论一致。
- 以业务锚点定位：写菜单、业务字段、参数、流程、接口名称或统计口径；这些锚点必须来自工作项或已解析附件，不得猜测。
- “需求类别”之后必须且只能写一行 `路径`，固定格式为 `- **路径**：菜单路径：<业务菜单层级>；操作路径：<业务操作步骤>`。多类别共用该行，不重复。
- 菜单路径写功能所在的业务菜单层级，操作路径用 `→` 写从入口到触发结果的业务步骤；无法从工作项、已解析附件或唯一菜单索引确认时，对应部分写“未确认”，不得猜测。
- `路径` 只写业务内容，不得包含技术仓库、工程目录、类、方法、接口、Mapper、表或字段名。
- 每个必需维度均写明确值；无影响或无此项时写“无”及适用边界，不能留空。
- **`现有行为/数据影响`（优化类类别必填）**：明确本次修改是否触及既有计算、写入、状态或数据，以及对既有行为的回归影响；无影响时写"无，仅 UI 层"及适用边界，不能留空。区别于 `影响范围`：后者指本次变更覆盖到哪些功能边界，前者指**对既有计算/数据/状态是否产生回归影响**——两者都要写，不可互相替代。
- **参数不得为填模板而新增**：只有工作项/附件明确要求参数控制，或已证实现有同类功能必须按机构/现场开关时，才提出参数；否则写“无新增参数”，不得以灰度、回退、现场差异为由主动扩张方案。
- **场景逐项覆盖**：写作前把原始描述中的入口、加载/选择/保存/打印等触发阶段、条件和期望动作逐项映射；不同触发点不得合并成一个泛化场景。跨状态/历史处理的需求另建“对象状态 × 事件 × 已处理状态 × 期望动作 × 验收结果”矩阵；新增、修改、撤销/停用、重复、部分完成和失败重试中任一会改变结果的组合均不得省略。
- **界面方案先对齐产品现状**：颜色、标签、图标、列位和交互方式必须来自已核实当前页或同类页面规则；实施提出的视觉方案只作候选。提示/提醒必须写清触发条件、展示位置或形态、默认文案、是否阻断及后续动作；触发条件或阻断语义不清时回退 QC，样式可按现状默认但仍须写出默认。未核实设计规则时记 `evidence_gaps` 并走人工复核，不得 AUTO。
- 禁止“请开发处理”“优化XXX功能”等空泛描述；禁止只复述标题或使用模板占位符。
- 图谱中的类、方法、调用链、Mapper、表字段仍是内部佐证；只可写原始证据已明确的业务字段、参数或数据规则。
- 界面布局和交互用文字说明位置、触发和结果；不生成或上传 HTML、截图等额外附件。
- 该规则生成的是受控 Markdown 行格式；不写 HTML，执行器负责安全渲染。
- 报表不合规时，说明合规限制和不能自动实施的原因；本 skill 不关闭工作项。已开发接口若只是联调/现场配合且没有新增分析面，准入阶段直接 `SKIP-ANALYSIS`，不会生成分析者描述；只有确实需要分析字段映射、接口契约、异常处置或验收逻辑的调试事项才使用 `third-party-debug`。
- **业务合理性判断（必做·先于落笔）**：分析者描述不得无审核照搬需求方给的方案、校验逻辑或提示文案；落笔前先做业务合理性判断——**合理则沿用**需求方案/文案（可引用原话，不必强行改写），**不合理或有更优解则优化**为专业方案并简述理由（一句话，让产品/研发能据理否决）。判断依据来自业务常识 + 工作项/附件事实，不凭空。直接影响实现正确性的方向性歧义，可在方案内标注主推断 + 理由（是非题），不堆积为开放性待确认。
  - 不得以候选实现、未确认根因或“按现有逻辑”替代业务结论；方向、根因、范围、取数口径或权限口径不清时，按闭环规则回退 QC，而非在本区编造默认。
  - **子模式·症状性规避方案（治标警惕·强约束）**：当需求是**性能/异常抱怨**（卡顿/慢/等待/超时/延迟/崩溃/数据错乱等）而需求方（常见实施/现场）给的方案是**使用层规避**（限记录数/分批/加提醒/临时截断/阈值上限等）时，**不得照搬该规避方案分析**——异常量级的数据不应致异常卡顿/错误，规避方案治标可能掩盖真实缺陷。须**回退质控** `NEED-REVIEW`（产品+研发负责人，先排查根因），**不为本类需求写变更方案/优化方案**（见 `config/analysis-rules.md` §1 治标警惕、`config/qc-rules.md` §6a、`references/qc-checklist.md` §一 #10）。仅在确认根因后、或确认上限确为合理产品策略（重新触发分析）时才落分析。
  - **子模式·功能性工作项中的 BUG**：描述若表现为既有功能错误、字段有值/为空不一致、条件分支结果不同或“原本应当”，优先用 `bug-fix` 描述现象、复现条件、影响范围、修复方向与回归影响；不得仅因标题含“优化/调整”选 `existing-ui-simple` 或 `print-adjustment`。字段类 BUG 必须先完成全部取值分支检查。

## 二、格式红线（执行器硬约束·最高优先级）

> 以下来自 `pipeline.py` 的 `validate`/`render` 逻辑，**违反任一条 `apply` 阶段必报错停止**。上一轮工作项 254677 曾因「对接流程」维度写成多行子列表被拒（`分析者描述含不支持的 Markdown 行`），务必避免。

- **维度行必须单行**：每个维度写成 `- **维度名**：非空内容`，冒号（全角 `：`）后**至少一个非空白字符**。复杂需求的多个独立改造点可补充扁平编号行 `1. **改造点**：…`，每行只表达一个改造点，最多 8 项；不得嵌套或写成长段。
- **禁止的行类型**：空维度值（`- **维度**：` 后留空）、子列表（缩进 `- …`）、表格（`| … |`）、代码块（```` ``` ````）、纯文本段落、`####` 及更深标题。`## 三、分析者描述` 章节内**只允许**：一个 `- **需求类别**：…` 行、一个 `- **路径**：…` 行、若干 `### <id>（中文名）` 类别标题、每个标题下若干 `- **维度**：…` 维度行，以及复杂需求的扁平编号改造点行。
- **类别标题格式**：`### <id>（<中文名称>）`，必须用**全角括号** `（）`；`<id>` 只能是小写字母与连字符（如 `third-party-new`），且与计划 `analysis_description.categories` 完全一致。
- **路径行格式**：必须且仅一行 `- **路径**：菜单路径：<…>；操作路径：<…>`，两部分都非空，用**全角分号** `；` 分隔。
- **占位符/空泛话术**（作用于整个 `change-plan`）：不得出现 `<…>` 尖括号占位符、`TODO`，以及 `请开发处理`、`已和项目沟通，关闭`、`没问题，关闭`、`要求的详细分析，包含分析结果、疑问及要求完成效果等`、`优化XXX功能` 等空泛话术。

> `validate` 只校验“必需维度是否齐全且非空”，可能放过不合规的多行；真正的逐行严格校验发生在 `apply` 的渲染阶段。因此**写作时即按单行格式落笔**，不要依赖 `validate` 通过来推断 `apply` 安全。

## 三、书写质量标准

**核心原则**：简单需求 → 简短精准（一两句说清绝不多写）；复杂需求 → 详略得当（多模块/多接口/多参数才展开）。**黄金标准**：开发/测试看完能直接执行，无需追问。

**必须避免的劣质描述特征**：
1. **废话连篇**：模板占位符填充、无实质内容（如“要求的详细分析，包含分析结果…”）。
2. **有头无尾**：只说要做什么，不说具体方案或参数（如“优化XXX功能”）。
3. **无上下文**：只有标题级描述，看不出业务场景（如“字段调整”不知哪个菜单/字段、“接口对接”不知哪个项目/接口）。
4. **歧义表达**：可产生多种理解（如“默认展示”不知展示什么、在哪展示）。

**合格的优质描述特征**：
1. **精准定位**：指明具体的菜单、业务字段、参数编号。
2. **操作明确**：说明“做什么”和“怎么做”。
3. **边界清晰**：参数取值、适用范围、影响边界。
4. **长度适中**：能一句话说清的绝不多写。

## 四、受控类别与必需维度（与 `pipeline.py` 一致·速查）

每个类别在方案中用 `### <id>（中文名称）` 作为三级标题，标题下逐行输出下表全部维度，格式为 `- **维度**：明确内容`（单行）。

### 简单需求短输出 `concise-v2`（新计划默认）

单一 `existing-ui-simple`、`print-adjustment` 或 `data-management`，且改动点不超过 3 个、无跨模块/复杂规则时，新计划优先写 `analysis_profile=concise-v2`。`路径` 已表达入口与操作场景，本区只保留“核心改造点”；仅当需求容易被误扩展时才额外写“不涉及范围”。不得再用“生效场景”重复路径。

| `existing-ui-simple` | 核心改造点 |

| `data-management` | 核心改造点 |

## 五、各类别书写要点与优质示例

> 示例**仅示范内容与单行维度写法**，不是完整产物；实际应基于工作项与已解析附件的真实锚点填写。所有示例行均为合法单行维度格式，可直接效仿。

### report（报表）
- **书写要点**：①明确报表数据是否符合政策规范（如防统方）；②逐一说明每列含义；③明确统计边界（含/不含哪些）；④标注特殊统计口径。
- **优质示例**：
  - `- **合规性**：符合医疗数据统计使用规范，无防统方风险。`
  - `- **列定义**：西药处方（不含中成药的纯西药）、成药处方（含中成药）、中药饮片处方（草药处方）。`
  - `- **统计口径**：肌肉注射针次数只统计肌肉注射诊疗项目、不含疫苗接种；中医非药物疗法统计“中医治疗”项目开具数量，不含退费和未收费。`

### third-party-debug（第三方已开发接口调试）
- **准入边界**：本类别不承接“接口已经开发、只需研发配合联调”的纯支持单；该类必须在准入路由判 `SKIP-ANALYSIS`。仅当调试事项明确涉及字段映射、请求/响应契约、异常处置、触发时机或验收逻辑的新增/调整，才进入本类别。
- **书写要点**：①明确接口身份与已开发基线；②说明本次需要分析的契约/规则变化及触发时机；③列出双方职责、验收结果与不涉及范围。不得用“请研发配合调试”作为唯一改造内容。
- **优质示例**：
  - `- **已开发接口**：体检系统与 HIS 的收费状态回传接口已开发完成，现有回传只覆盖成功状态。`
  - `- **协作事项**：本次补充失败状态码映射与重试后的验收口径；体检系统提供失败报文，HIS 按已确认映射落状态并回传处理结果，不调整收费业务规则。`

### third-party-adjustment（第三方既有接口调整）
- **书写要点**：①说明现有接口变更点（从→到）；②评估影响范围；③是否需参数控制；④字段取值逻辑与映射转换。
- **优质示例**：
  - `- **现有接口变更**：HIS 与医保接口的就诊类型字段由原 2 个取值扩展为 4 个。`
  - `- **影响范围**：门诊收费、住院结算共用的医保上传链路。`
  - `- **参数控制**：新增参数控制是否启用新取值，未启用现场保持原逻辑。`
  - `- **取值逻辑**：普通门诊=1、急诊=2、专家=3、特需=4，按就诊记录类型映射上传。`

### third-party-new（第三方新接口）
- **书写要点**：①业务背景与数据流向；②对接流程（步骤化但压成单行）；③触发时机；④当前数据能否支撑必填字段、对方返回是否需落表；⑤是否涉及业务功能改造、参数控制与字段映射。
- **优质示例**：
  - `- **业务背景**：伊宁区域中心药房接入快享平台，与中心药房双向药品调拨并同步追溯码。`
  - `- **对接流程**：调出审核后调 YY142 上传调出单并扣减库存；调入调 YY143 下载调拨单后审核转入药库入库。`
  - `- **触发时机**：调出“上传调拨单”、调入“下载调入单”按钮触发，不做定时任务。`
  - `- **数据支撑与字段映射**：HospitalCode/HospitalName/StoreCode/StoreName 固定取值，明细含 UniCode/Name/Quantity/批次/追溯码 CodeList，按《标准接口文档》字段映射。`
  - `- **返回数据处理**：同一调出单一次性上传、重复上传仅首次接收；下载按分页/时间区间拉取。`
  - `- **影响与参数控制**：新增“快享药品调拨”菜单，影响库存与追溯码；固定参数需可配置，避免硬编码误用到其它现场。`

### existing-ui-simple（既有功能简单界面优化）
- **书写要点**：①需求背景；②涉及功能模块；③具体修改方案（含判断逻辑）；④是否参数控制；⑤显示/交互位置与完整提示文案；⑥影响范围；⑦现有行为/数据影响（对既有计算/写入/状态/数据的回归影响，无则写"无，仅 UI 层"及边界）。
- **优质示例**：
  - `- **需求背景**：精神类药物需按身份证与间隔天数校验是否可再次开立。`
  - `- **修改方案**：保存门诊西药处方时取同身份证上次精神类药物费用时间，判断是否过配置天数，未过则拦截。`
  - `- **参数控制**：新增参数配置间隔天数（今早 10 点开药、配置 2 天则 2 天后 10 点可再开）。`
  - `- **显示与交互位置**：保存门诊西药处方时触发校验，拦截提示“该身份证 XXX 姓名 XXX 于 XXX 开立精神药物处方 XXX，不允许开方”。`
  - `- **影响范围**：仅精神类药物（分类代码为 2）的门诊西药处方保存。`
  - `- **现有行为/数据影响**：新增保存前校验，不改变既有费用计算、写入或处方状态流转；拦截后业务人员调整开方内容再保存，无既有数据回归影响。`

### existing-query-simple（既有简单查询调整）
- **适用边界**：只新增或调整一个查询条件，且结果列表已有同一业务标识字段可复用，不改计算、写入、状态、权限或关联视图时使用；重点让研发明确改哪里、按什么规则查、哪些内容不改。
- **书写要点**：只写三项，禁止为凑维度重复需求背景、空值、权限或验收描述；“不涉及范围”必须明确复用既有结果列、不新增列，并列出不改的业务能力。
- **优质示例**：
  - `- **查询入口与条件**：门诊费用查询条件区新增“医保结算单号”输入项，非必填。`
  - `- **查询规则与流程**：输入完整单号后与既有筛选条件共同查询，精确定位对应费用记录；未输入时沿用原查询。`
  - `- **不涉及范围**：复用结果列表既有“医保结算单号”列，不新增列；不修改收费、结算、退费、金额计算及数据权限。`

### existing-query-adjustment（既有查询能力调整）
- **适用边界**：涉及新增结果列、跨页面联动、权限/脱敏、复杂组合筛选、取数口径或业务规则变化的查询调整使用；不可用 `existing-query-simple` 省略完整查询闭环。
- **书写要点**：①说明查询入口、条件名称、输入方式和必填性；②写明精确/模糊匹配、格式校验及与原条件的组合逻辑；③写清结果列表新增或复用的字段、列名/位置和展示值；④交代未输入、无匹配、重复或格式异常时的行为；⑤说明详情、导出、打印等关联视图是否同步，以及沿用的权限/脱敏范围；⑥列正常、空值、无结果、组合筛选和权限场景验收。
- **业务标识规则**：新增业务标识类查询条件（单号、编码、证件号等）时，先核实结果列表是否已有同一标识字段：已有则明确写“复用既有字段、不新增列”；仅在工作项、已解析附件或已核实页面证实缺失时新增列。没有证据时不得从“新增查询条件”推断“新增结果列”；如果不展示，必须有工作项或已解析附件支撑的业务理由，不能默认省略。
- **信息缺口处理**：取数口径、匹配方式、权限/脱敏或关联视图范围不明且会影响正确性时，属于 spec 歧义，回退阶段一 `NEED-REVIEW`；仅列宽、排序、空值文案等呈现细节可按合理默认写入 §六假设。
- **优质示例**：
  - `- **查询入口与条件**：门诊费用查询条件区新增“医保结算单号”输入项，非必填；为空时保留既有患者、日期、费别和状态查询。`
  - `- **匹配规则与组合逻辑**：输入完整医保结算单号时精确匹配，并与已输入的日期、费别和状态条件同时生效。`
  - `- **结果字段与展示**：结果列表增加“医保结算单号”列，展示匹配到的完整单号；若已有同义列则复用该列并保持既有位置。`
  - `- **空值与异常处理**：未输入单号不改变原查询；无匹配时沿用既有空结果提示；格式校验规则未在需求中定义时不得臆造。`
  - `- **关联视图与权限**：账单详情、导出和打印不新增展示；沿用门诊费用查询既有管理员可见范围与脱敏规则。`
  - `- **验收场景**：有效单号定位对应费用并显示单号列；空单号保持原结果；与日期组合筛选结果正确；无匹配返回空结果；无权限角色不可突破既有可见范围。`
  - `- **影响范围**：仅门诊费用查询的条件与结果列表，不触发收费、结算、退费、票据或费用数据修改。`

### existing-complex（既有功能复杂调整）
- **书写要点**：①涉及条线/模块；②改造内容；③改造流程；④改造范围；⑤风险与项目注意事项。两个及以上独立改造点必须在“改造内容”后按 `1. **名称**：…` 分行列出；每项对应一个触发条件和可验收结果，禁止混写成并列长句。
- **优质示例**：
  - `- **涉及条线与模块**：门诊收费、医保上传、财务报表三条线联动。`
  - `- **改造内容**：门诊收费费用明细结构调整，同步影响医保上传字段与财务报表取数。`
  - `- **改造流程**：先改收费明细 → 联调医保上传 → 回归财务报表取数。`
  - `- **改造范围**：全部门诊收费场景，住院不受影响。`
  - `- **风险与项目注意事项**：需评估各现场医保接口差异，灰度上线并保留回退。`

### new-feature（新功能开发）
- **书写要点**：①完整业务流程；②功能入口；③参数/权限/数据权限/脱敏/历史数据/第三方影响逐项交代；④数据存储与扩展性；⑤文字交互说明。
- **优质示例**：
  - `- **业务场景**：新增“快享药品调拨”菜单，实现与快享平台双向药品调拨。`
  - `- **功能方案**：调出新增单据+审核+上传+扣库存；调入下载+审核+入库，菜单参考现有药品调拨。`
  - `- **参数控制**：医院/库房标识参数化配置。`
  - `- **权限与数据权限**：药库管理权限范围内，按库房隔离。`
  - `- **脱敏与历史数据**：无脱敏需求；历史调拨单不受影响。`
  - `- **数据与第三方影响**：对接快享 YY142/YY143，库存与追溯码数据双向同步。`
  - `- **文字交互说明**：上传/下载结果前端给出成功/失败反馈并维护单据状态。`

### print-adjustment（打印调整）
- **书写要点**：①打印内容来源；②区分前端显示与打印显示；③模板维护责任方；④数据存储位置。
- **优质示例**：
  - `- **打印场景**：门诊医生站打印病历时需打印全草药备注说明。`
  - `- **单据类型**：草药处方打印。`
  - `- **修改内容**：处方增加“备注”字段，前端不展示、仅打印显示。`
  - `- **模板处理**：由项目维护到打印模板中显示。`
  - `- **数据源**：备注取自药品信息维护的“备注”字段。`

### bug-fix（BUG 修复）
- **书写要点**：①描述问题现象而非标题；②已有相关参数与已知条件；③明确修复范围；④对现有逻辑的影响。
- **优质示例**：
  - `- **问题现象**：预防接种号当前可不写病历直接开处方，但可开任意药品类别。`
  - `- **复现步骤或已知条件**：参数 M482 已控制预防接种号免写病历开方，但未限制药品类别。`
  - `- **修复方案**：在 M482 基础上，限制预防接种号只能开账目类别含生物制品和疫苗的处方。`
  - `- **现有逻辑影响**：仅增加药品类别限制，不影响其他号别开方逻辑。`

### data-management（数据管理）
- **书写要点**：①查询/筛选条件的增加；②新增字段的显示位置；③导入/导出格式要求；④数据来源。
- **优质示例**：
  - `- **操作场景**：处方管理需按药房查询（原仅支持按医生查询）。`
  - `- **数据对象**：门诊处方记录。`
  - `- **操作规则**：查询条件新增“药房”筛选项。`
  - `- **批量或导入导出**：导出 Excel 需含新增“联系电话”列。`
  - `- **数据校验**：联系电话取自患者档案，空值允许。`

### permission-config（权限/参数配置）
- **书写要点**：①列出所有涉及参数；②每个参数取值含义；③参数值对应功能表现；④测试验证点。
- **优质示例**：
  - `- **权限场景**：建档挂号页显示、结束就诊后按钮状态、草药代煎默认用法。`
  - `- **参数编号与名称**：D201（建档挂号页是否显示）、D202（结束就诊后下一按钮是否禁用）。`
  - `- **参数值域**：D201/D202 均为开/关（1/0）。`
  - `- **控制效果**：D201 开则显示建档挂号页；D202 开则结束就诊后下一按钮不禁用，关则保持原模式。`
  - `- **验证点**：各参数开关下页面表现与草药代煎勾选后默认用法是否符合预期。`

### performance（性能优化）
- **书写要点**：①明确慢的具体操作；②优化方向（如前端校验改后端）；③性能指标（如有）；④**治标警惕**——若需求方给的是限记录数/分批/加提醒/临时截断等**使用层规避**而非根因修复（加索引/分页/异步/缓存/重构），视为症状缓解，须**回退质控排查根因**，**不得**把该规避方案写进"优化方案"沿用。
- **优质示例**：
  - `- **性能问题**：门诊处方列表数据量大时加载超过 3 秒。`
  - `- **影响范围**：门诊医生站开方时的处方查询。`
  - `- **优化方案**：由前端全量加载+过滤改为后端分页+条件查询。`
  - `- **预期效果**：列表加载降至 1 秒内。`

### mobile-adaptation（移动端/多端适配）
- **书写要点**：①对比 Web 端和移动端差异；②数据共享机制；③移动端特殊限制。
- **优质示例**：
  - `- **业务场景**：Web 端可维护的随访计划，移动端需查看与执行。`
  - `- **涉及功能**：随访计划列表、随访记录填写。`
  - `- **数据同步逻辑**：移动端离线缓存、联网后同步至 Web 端同一数据源。`
  - `- **与 Web 差异**：移动端不支持批量导入，仅支持单条填写与拍照上传。`

## 六、必须避免的 5 类问题（错误 ↔ 正确）

| 问题 | 错误写法 | 正确写法 |
|---|---|---|
| 1. 正确的废话 | “请开发处理。”/“已和项目沟通，关闭。” | 简单需求一句话说清，复杂需求才展开 |
| 2. 仅复制标题 | 标题“门诊处方增加字段”→描述“门诊处方增加字段” | “门诊处方管理新增XX字段，用于存储XX信息” |
| 3. 缺少关键定位 | “优化XXX功能” | “XX菜单的XX功能，在XX场景下需要调整为……” |
| 4. 遗漏参数编号和取值 | “增加参数控制” | “新增参数 DXXX 控制：1=显示XX按钮；0=隐藏” |
| 5. 产生歧义 | “默认展示” | “默认展示在XX位置，格式为XXX” |

## 七、长度参考（非硬性·执行器不按字数判，仅作详略指引）

| 需求复杂度 | 建议篇幅 | 适用类别示例 |
|---|---|---|
| 纯界面/打印/只读导出小调整 | `concise-v2` 核心改造点，约 40-180 字；非明显边界按需补充 | `existing-ui-simple`、`print-adjustment`、`data-management` |
| 参数控制类 | 2-5 句、约 50-100 字 | `permission-config`、`bug-fix` |

## 八、自检

1. `路径` 是否同时写清菜单路径和操作路径，且未混入仓库、代码或接口信息？
2. **每个维度是否都是单行 `- **维度**：非空内容`**，没有编号/子列表/表格/代码块/空维度？（格式红线）
3. 开发和测试能否仅凭方案知道改什么、在哪个业务场景生效、怎样验收？
4. 每个参数、默认值、统计包含/不包含范围和异常表现是否明确？
5. 定位精准吗？能否从描述中直接找到对应的菜单/业务字段/参数编号？
6. 简单需求是否避免了无关展开；复杂需求是否给出流程、范围和风险？
7. 有歧义吗？是否存在多种理解的表达？
8. `analysis_description.categories`、需求类别行和三级标题是否完全一致？
