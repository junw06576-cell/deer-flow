# 事前质控规则

> **适用阶段**：产品经理在 TFS 中拿到"已创建/活动"状态的需求后，**在动手分析之前**对需求做的质量检查与可处理性判断。
> **核心目标**：把不符合时效要求、描述不清晰的需求提前筛除，避免无效分析浪费工时。
> **数据来源**：`需求分析方法.md` 中的"需求质控"章节，并结合实际工作场景补充完善。

---

## 一、质控执行流程

```
新需求进入待分析队列
        ↓
  ┌──────────────────────────────┐
  │ 1.时效质控                    │  → 判定需求是否可在迭代周期内交付
  │   - 需求类型预判（排除软件质量类）│
  │   - PIMIS 优先级质控           │
  │   - 期望日期质控               │
  └──────┬───────────────────────┘
         ↓ 通过
  ┌──────────────────────────────┐
  │ 2.内容质控                    │  → 判定需求描述是否清晰、可分析
  └──────┬───────────────────────┘
         ↓ 通过
   进入分析阶段（参考 02_需求分类规则.md）
```

任一环节不通过时，按本规则对应的处置方式处理，**不要进入分析阶段**。质控环节仅做可处理性判断，不修改 TFS 状态。

> **说明**：查重质控作为预留项，当前不作为质控内容，后期再完善具体规则（详见"四、查重质控（预留）"）。

## 二、时效质控

### 1. 需求类型预判（软件质量类排除）

**字段**：TFS `需求类型`

**判断逻辑**：

| 条件 | 处理方式 |
| ---- | -------- |
| 需求类型 = `软件质量` | 不需要质控，不在本组处理范围 |
| 需求类型 = `功能性的` | ✅ 进入后续时效质控 |

**处置动作**：
- 需求类型为 `软件质量` → 不进入后续质控与分析流程

---

### 2. PIMIS 需求优先级质控

**字段**：TFS `PIMIS需求优先级` 字段（允许为空，为空时**不做本项质控**）
**适用范围**：仅针对 `需求类型` 为 `功能性的` 的需求

#### 功能性需求时效表

| 优先级 | 是否处理 | 处置说明 |
| ------ | -------- | -------- |
| A 级   | ❌ 不可处理 | A 级要求研发 6 天内、测试 3 天内完成，合计 12 天。而我方迭代周期为两周（14 天），研发需在迭代日期前一周最后一个工作日提交代码，时间冲突，**通常无法按时交付**。如确需处理，需研发负责人单独确认 |
| B 级   | ⚠️ 谨慎处理 | 合计 21 天，跨 1-2 个迭代。需评估当前迭代剩余容量后再决定是否安排 |
| C 级   | ✅ 正常处理 | 合计 30 天，约 2 个迭代，可正常排期 |
| D 级   | ⏸️ 缓期处理 | 缓期处理，30 日内由分析与现场再确认。无需处理的不再处理，仍需处理的重新确认优先级与完成时间 |

---

### 3. 需求期望日期质控

**字段**：TFS `期望日期` 字段（允许为空，为空时**不做本项质控**）
**解析规则**：期望日期解析为标准日期（ISO 或 `年月日`）。
**迭代日历来源（实查）**：调 `tfs_client.py list-iterations`（`--project` 用工作项 teamProject、`--expected-date` 可选；完整命令见 `../_lib/COMMANDS.md`），直查 TFS 分类节点 API（`classificationnodes/iterations`）取**官方 `startDate/finishDate`**。**不再从工作项 `System.IterationPath` 字符串解析日期**——迭代路径可能停在项目根（如 `NETHIS5.5`）而无可解析日期。

**判定基准：`finishDate < 期望日期`**——需求要在期望日期**之前**的迭代里交付完。`list-iterations` 返回的 `matched` 即 `finishDate ≤ 期望日` 中 `finishDate` 最大者（能赶上的最晚迭代）。

| 情况 | 是否处理 | 处置说明 |
| ---- | -------- | -------- |
| `matched` 存在，且当前日期 ≤ `matched.finish − 7 天`（代码提交截止） | ✅ 正常处理 | 时间充裕，可排入该迭代 |
| `matched` 存在，但当前日期已过 `matched.finish − 7 天` | ⚠️ 谨慎处理 | 时间紧张，需评估能否赶上代码提交截止 |
| `matched=null`（期望日期早于所有迭代 `finishDate`） | ❌ 不可处理 | 无迭代能在期望日前交付，需退回现场重新协商期望日期或调整优先级 |
| `list-iterations` 查询失败 / 项目无迭代 | ❌ 不可处理 | 交排期方/现场补充迭代日历，**不得猜测日期**（记 `iteration.timing=unavailable`） |

> **代码提交截止 `−7 天`**：研发需在迭代 `finishDate` 前一周最后一个工作日提交代码，故 `matched.finish − 7 天` 为代码提交截止日；当前日期若已过此截止日，该迭代已来不及。

---

### 4. 时效质控组合判定规则

当 PIMIS 优先级与期望日期同时存在时，按以下规则组合判定：

#### 4.1 单项直接判定（无需组合）

| 条件 | 判定结果 | 处置方式 |
| ---- | -------- | -------- |
| PIMIS 优先级 = A 级 | 质控不通过 | 不可处理（如确需处理需研发负责人确认） |
| PIMIS 优先级 = D 级 | 缓期处理 | 按 30 日再确认流程处理，不直接进入分析 |
| 期望日期判定为不可处理 | 质控不通过 | 与现场沟通调整期望日期或优先级，调整后重新质控 |

#### 4.2 组合判定（PIMIS B/C 级 + 期望日期）

| PIMIS 优先级 | 期望日期判定 | 组合判定结果 | 处置方式 |
| ------------ | ------------ | ------------ | -------- |
| B 级 | 不可处理 | ❌ 质控不通过 | 与现场沟通调整期望日期，调整后重新质控 |
| B 级 | 谨慎处理 | ⚠️ 谨慎处理 | 需评估当前迭代剩余容量，且需研发确认能否在 21 天周期内交付 |
| B 级 | 正常处理 | ⚠️ 谨慎处理 | PIMIS B 级本身需谨慎，按 B 级时效（21 天）安排 |
| C 级 | 不可处理 | ❌ 质控不通过 | 与现场沟通调整期望日期，调整后重新质控 |
| C 级 | 谨慎处理 | ⚠️ 谨慎处理 | 需评估当前迭代剩余容量后再决定 |
| C 级 | 正常处理 | ✅ 正常处理 | 时效充裕，可正常排期 |

#### 4.3 字段为空时的判定

| 条件 | 判定结果 | 处置方式 |
| ---- | -------- | -------- |
| PIMIS 优先级为空 + 期望日期为空 | ✅ 正常处理 | 按普通需求处理，安排到下个迭代 |
| PIMIS 优先级为空 + 期望日期不可处理 | ❌ 质控不通过 | 与现场沟通调整期望日期 |
| PIMIS 优先级为空 + 期望日期谨慎处理 | ⚠️ 谨慎处理 | 按期望日期判定处理 |
| PIMIS 优先级为空 + 期望日期正常处理 | ✅ 正常处理 | 按期望日期判定处理 |
| PIMIS 优先级 A/B/C/D 级 + 期望日期为空 | 按 PIMIS 优先级单项判定 | 按功能性需求时效表处理 |

> **判定原则**：当两项都存在且其中任一项判定为"不可处理"时，组合判定即为"质控不通过"；当两项判定结果不一致时，按"取严"原则处理（即取更严格的判定结果）。

## 三、内容质控

### 1. 标题项目信息检查（AI 自主判断·不做字典限制）

**规则**：需求标题中**应包含**项目信息（项目 / 客户 / 区域 / 大区归属），便于快速定位需求来源。
**判定方式（AI 自主判断）**：由 AI 判断标题是否含**可识别的项目归属信息**——下方的“项目关键词字典”仅作**参考示例，非硬性限制**；AI 可识别字典之外的合理归属（真实地名、客户/机构名、区域/大区名等）。能识别出归属即通过；仅当标题**完全无任何项目/区域/客户/大区归属信息**时才判不通过。
**数据来源（参考）**：`基层医疗标题项目名称知识库.md` 汇总的项目清单 + 客户/机构清单，整理为下方参考字典，供 AI 与维护者参考，**不作为通过/不通过的限制条件**。

### 项目关键词字典（参考·非限制·已外置）

> 本字典已外置为独立参考文件 [`project-keyword-dictionary.md`](project-keyword-dictionary.md)，**仅当标题归属存疑、需核对参考时才读**（归属清晰时不读，以省上下文）。判定规则与 AI 自主判断口径见上方 §三.1 与 `../config/qc-rules.md` 规则 4。

### 质控动作（AI 自主判断）

- ✅ AI 判定标题含**可识别的项目/客户/区域/大区归属**（含但不限于上述参考字典） → **质控通过**
- ❌ AI 判定标题**完全无任何项目/区域/客户/大区归属信息** → **质控不通过**（`NEED-INFO`，责任方：实施/创建者）

### 2. 需求方向 / 根因一致性（治标警惕）

**背景**：实施/现场同事提需时，常把"自己想到的处理方案"直接写进需求，而该方案未必触及问题根因——尤其对**性能/异常抱怨**，需求方倾向于给"使用层规避"（限记录数、加提醒、分批、临时截断），这往往**治标不治本**，可能掩盖真实缺陷。AI 不得照搬该规避方案直接分析，须先做根因判断。

**判断逻辑（AND 触发）**：

| 条件 | 关键词（命中任一即算） |
| ---- | ---- |
| 需求含**性能/异常抱怨** | 卡顿、慢、等待、超时、延迟、崩溃、卡死、无响应、数据错乱、报错、性能 |
| **且** 方案为**使用层规避**（非根因优化） | 上限、提醒、分批、限制、阈值、不超过、最多N条、临时截断、规避、绕过 |

- 两者同时命中 → **方向类存疑** → `NEED-REVIEW`（责任方 **产品 + 研发负责人**），清单 item（`priority:P0`）问"是否先做根因排查，而非套上限/提醒"。
- **不触发**：方案是根因优化（加索引/分页/异步/缓存/重构），或纯性能优化诉求且无规避关键词——正常走原流程。

**判定基准**：异常量级的数据**不应**致异常卡顿/错误（如几十条记录打开等待 20 秒、几百条数据就报错）属反常，大概率存在真实性能/逻辑缺陷（全量加载、N+1 查询、缺索引、前端阻塞渲染、循环调用接口等）。此时"限条数/加提醒"只是让用户绕开慢点，**不解决缺陷**，且新增护士多建护理单等操作反而**降低业务效率**。

**处置动作**：
- 命中 → 打 `PM-AI-QC-NEED-REVIEW`，清单写明"需求方方案为症状缓解，建议先由研发排查根因（疑似 XXX）后再定方案"，交产品 + 研发负责人；**不进入分析**（不为其写变更方案）。
- 责任方补充根因结论（确认是真缺陷→按缺陷修复；或确认上限确为合理产品策略→重新触发分析）后再进入分析。

**示例（258894 式）**：
- ✅ 命中：需求"动态护理单录入较多条数后打开卡顿，等待近 20 秒"（性能抱怨·卡顿/等待）+ 方案"录入满 36 条强提醒新增护理单"（使用层规避·上限/提醒）→ 几十条数据不应致 20 秒卡顿，规避方案治标 → `NEED-REVIEW`（产品+研发），挡回排查打开慢点（疑似全量加载/渲染阻塞/N+1）。
- ❌ 不命中：需求"门诊处方列表数据量大时加载超过 3 秒"（性能抱怨）+ 方案"由前端全量加载改为后端分页+条件查询"（根因优化·分页）→ 方案触及根因，正常走分析（`performance` 类别）。
- ❌ 不命中：需求"给某字段加个非空提醒"（无性能/异常抱怨）→ 不触发本规则。

> 与 `config/qc-rules.md` §6a、`references/qc-checklist.md` §一 #10 为同一规则的详细源；改三处一起改。

## 五、质控结果处置汇总

> **说明**：质控环节**不修改 TFS 状态**，仅对需求做可处理性判断。TFS 状态的变更在分析阶段进行（详见 `04_迭代安排规则.md`）。

| 质控结果 | 处置方式 |
| -------- | -------- |
| 需求类型为软件质量 | 不需要质控，不在本组处理范围 |
| PIMIS 优先级 A 级 | 质控不通过（确需处理需研发负责人确认） |
| PIMIS 优先级 D 级 | 缓期处理，按 30 日再确认流程 |
| 期望日期不可处理 | 与现场沟通调整期望日期或优先级 |
| 时效质控组合判定为质控不通过 | 与现场沟通调整，调整后重新质控 |
| 时效质控组合判定为谨慎处理 | 评估当前迭代剩余容量后决定是否进入分析 |
| 标题无可识别项目归属（AI 判定） | 质控不通过（NEED-INFO，交实施/创建者） |
| 全部通过 | 进入分析阶段 |
