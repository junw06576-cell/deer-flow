# 经验记忆规范（skill-memory）

> 单一权威源：跨运行、本机、不入库的经验先验。启动时尽力读取 `过程文件/经验记忆.md` 作**提示性先验**；收尾时本轮产生**跨需求可复用**经验则追加一条。
> 触发与落位见 [`RUNBOOK.md`](RUNBOOK.md)（步骤 0 读、步骤 11 写）；硬约束见 [`../SKILL.md`](../SKILL.md)；与重分析诊断的关系见 [`../references/round-diagnosis-rules.md`](../references/round-diagnosis-rules.md) §4/§5。
> 本文件是**规范**（tracked、人写、很少动）；`过程文件/经验记忆.md` 是**数据**（本机、不入库、机器追加）。类比 `_lib/testing-log.md`（规范）↔ `过程文件/测试日志.md`（数据）；条目体例对齐 `过程文件/skill-feedback.md`。

## 0. 性质与边界

- **全程非交互**：无 `AskUserQuestion`、无追问、无等确认。
- **零 TFS 写入、零 pipeline.py 改动**：不进计划 JSON、不进 `run_*.json` 审计白名单、不生成附件。
- **向后兼容**：首轮 / 文件不存在 / 为空 / 不可读 → 静默 no-op，不影响任何终局或契约。
- **ADVISORY ONLY（同 round-diagnosis §5 性质）**：**不新增终局分支、不改 verdict→标签/状态映射、不改任何必填计划字段、不绕过硬约束**。与规则文件冲突时，**以规则文件为权威**，经验记忆仅作提示。
- **与 skill-feedback.md 分工**：本文件是【蒸馏后的生效先验】（祈使句、跨需求可复用）；`过程文件/skill-feedback.md` 是【逐轮诊断原始流水】（重跑+有补充才写）。两者不互相替代。

## 1. 文件契约

- 位置：`过程文件/经验记忆.md`（与 `测试日志.md` / `skill-feedback.md` 同级，处于 skill git 树之外，已被 `.gitignore` 覆盖）。
- 首次写入时创建文件并写表头（§4），表头仅写一次。
- **append-only（运行期）**：skill 在步骤 11 只追加 H2 条目，不覆盖/编辑/删除历史；出现矛盾/过时则追加新条目，并用可选 `取代` 明确旧条目不再应用（见 §5）。**维护者**可做合并重复/退役过时/毕业入规则等 curation——这是唯一允许编辑删除的场景（见 §8）。
- 不进 TFS、不入 Git、不进计划 JSON、不进 `run_*.json` 审计、不作为附件。

## 2. 读取规则（RUNBOOK 步骤 0，属"始终必读"集）

- **时机**：紧跟 `COMMANDS.md` / `RUNBOOK.md` 读取之后；与两者同属"始终必读"。
- **软读取**：文件不存在 / 为空 / 不可读 → 记 `memory=absent` 并继续；**不触发失败关闭**——本文件**显式排除在 [`../SKILL.md`](../SKILL.md) 启动检查"任一文件不可读→失败关闭"范围之外**（该失败关闭只覆盖 `_lib/COMMANDS.md` 与 `_lib/RUNBOOK.md`）。
- **应用方式（提示性先验）**：先按"类别 + 场景"筛选；命中条目的可选"不适用"条件时跳过，否则作为"须规避 / 重点守"的提示性上下文（与 round-diagnosis §5 同构），仍须核对当前证据和现行规则，不得因关键词命中就直接套用。
- **冲突处理**：先跳过所有被后续条目 `取代` 明确引用的旧条目；未写 `取代` 却出现同主题冲突时，以较新日期为兜底；日期相同则两条都不应用，回到当前证据和现行规则，并记为待维护。
- **不据此新增 verdict、不改必填字段、不绕过硬约束**；与规则文件冲突时以规则文件为准。
- **与 round-diagnosis 的关系**：二者均为提示性上下文，可叠加；不互相触发、不互相阻断。memory 中由既往同类诊断蒸馏来的条目，本轮一并规避。

## 3. 写入规则（RUNBOOK 步骤 11，在 测试日志 / skill-feedback 之后）

- **judgment gate，非每轮必写**：仅当本轮产生**跨需求可复用**的经验时才追加一条。两种触发：
  - **(a) 重分析诊断命中可沉淀类别**：即 round-diagnosis §3 中 `信息判断错误` / `输出质量不好` / `准入错误` / `规则·KB缺口` 之一；`信息不足·合理gap`（非缺陷）与 `其他`（执行层/环境）**不沉淀**。经验内容取自该诊断的"改进指向"。
  - **(b) 运行中踩坑/经验**：本轮运行中踩到、与具体业务内容**无关**、未来轮可复用的 **skill 层**经验（即写进测试日志「异常与改进」的"经验/踩坑"那类，**非该需求特定的业务信息**）。
- **首轮亦可写**：触发 (b) 不依赖重跑；触发 (a) 自然继承 `round_diagnosis=pending` 门控并叠加类别过滤。
- **不阻断**：追加失败（磁盘/权限）时，只在测试日志「异常与改进」补一句"skill-memory 追加失败：&lt;原因&gt;"并继续；**不得作为 ERROR、不停止本轮**。
- **写入去重（自动）**：追加前扫**同类别**现有条目；若已有同主题/同规则，仅在内容有实质补充或修正时追加一条合并后的新条目，并用 `取代` 引用已被完整覆盖的旧条目；无实质变化则不写——控制 active 条目数。
- **封顶信号（自动）**：未被 `取代` 的 active 条目超过约 40 或文件明显变大时，在测试日志「异常与改进」记一条"经验记忆待维护：合并重复/退役过时/毕业入规则"，**非阻断**。
- **与 skill-feedback.md 的关系**：触发 (a) 时，`skill-feedback.md` 条目照常写（原始流水），`经验记忆.md` 条目是其蒸馏镜像（祈使句）；两者不互斥也不互相替代。

## 4. 文件头与条目体例（对齐 skill-feedback.md）

首次创建时写一次表头；条目使用 H2 + `- 标签：内容` 普通列表。AI 判断是否应用一条经验只依赖"类别、场景、不适用、做法、取代"，不增加不参与判断的元数据。

**文件头**：

```md
# skill 经验记忆

> 每次产生可复用经验自动追加一条；启动时读作先验，不进 TFS、不入 Git。
> 使用：先按"类别 + 场景"筛选；命中"不适用"则跳过，其余仅作提示，仍须核对当前证据和现行规则。
> 冲突：被较新条目"取代"引用的旧条目不再应用；无取代关系时不写该字段。
```

**条目模板**：

```md
## <沉淀日期，如 2026-08-06> · <祈使句标题，即规则本身>
- 类别：<阶段·主题，取自下方受控词汇>
- 场景：<阶段 / 产物 / 触发条件>
- 不适用：<会造成过度套用的排除条件；可选，无则不写>
- 做法：<具体怎么做>
- 否则：<不守的后果；可选>
- 取代：<被本条完整覆盖的旧条目完整标题；可选，无则不写>
- 备注：<可选>
```

- 标题用**祈使句**（"禁用/避免/必做/先做X"），是 AI 识别的主钩子；正文每行一个要点、尽量单行，不展开叙述。
- **类别用受控词汇**，便于 AI 按阶段分组定位（首轮按"类别+场景"圈定相关条目再读做法）：`准入·路由｜质控·spec清晰度｜质控·时效｜质控·查重｜分析·描述｜分析·方案｜计划·结构校验｜执行·字段流转`；出现新阶段可在词汇表追加。
- `类别`、`场景`、`做法`必填；仅当某类相似场景容易误命中时写`不适用`，没有排除条件时省略。
- `取代`只在修正、否定或完整合并旧经验时填写，值使用旧条目的完整 H2 标题（日期 + 标题）；可引用多条。无取代关系时省略，不写"无"。
- 一条只表一条经验；多条经验分多条。标题只保留北京时间日期 `YYYY-MM-DD`，不写时分。
- 不写独立 `ID`、`来源`、需求号、`run_id` 或`状态`：这些元数据不参与本文件的场景匹配；原始追溯留在 `skill-feedback.md` / `测试日志.md`，条目是否生效由 `取代` 关系推导。

## 5. 矛盾与过时（append-only，不编辑旧条目）

- 要修正、否定或完整合并旧经验，**追加一条新条目**，并写 `- 取代：<旧条目完整标题>`；即使同一天追加，也依靠显式 `取代` 判断，不依赖时分或文件顺序。
- 读取时先建立取代关系：凡完整标题被任一较新条目 `取代` 引用的旧条目均跳过；旧条目仍留在文件中作历史留痕。
- 没有 `取代` 关系的条目默认都生效；若它们意外冲突，以日期较新的条目为兜底；日期相同则两条都跳过，并触发维护提示，后续由维护者补齐取代关系或完成 curation。

## 6. 工作示例

```md
## 2026-08-06 · 面向模型的提示语不得写入分析者描述/变更方案正文
- 类别：分析·描述
- 场景：用户补充信息里含"映射仅适用于本需求""排查方向"等面向大模型的提示时。
- 不适用：提示语本身就是需要交付给业务人员的正式需求内容时。
- 做法：区分「交付业务结论」与「面向模型的过程提示」——提示性话语只作 skill 侧上下文，不写入 TFS 描述/方案正文。
```

## 7. 与 round-diagnosis §3 类别的映射

| round-diagnosis §3 类别 | 是否沉淀到 `经验记忆.md` |
|---|---|
| 信息判断错误 | 是 |
| 输出质量不好 | 是 |
| 信息不足·合理gap | **否**（非缺陷） |
| 准入错误 | 是 |
| 规则/KB缺口 | 是 |
| 其他 | **否**（执行层/环境问题） |

## 8. 增长与维护（防止无限膨胀）

经验记忆是**暂存区**，不是归档库：稳定下来的教训应**毕业成规则文件**后从记忆移除，文件因此天然有封顶。四道闸：

1. **毕业入规则（维护者，主封顶）**：某条教训反复命中、内容稳定后，维护者把它写进对应规则文件（如 `analysis-description-writing-rules.md`），再从 `过程文件/经验记忆.md` 移除。规则文件是权威、自动随 skill 生效；memory 只留"刚发现、还没够稳成规则"的。
2. **写入去重（skill 自动，见 §3）**：追加前扫同类别；近重复不写，实质更新则追加合并条目并显式 `取代` 已完整覆盖的旧条目。
3. **封顶信号（skill 自动，见 §3）**：未被 `取代` 的 active 条目 >~40 或文件明显变大 → 测试日志记"待维护"提示。
4. **分级扩容（维护者，按需）**：条目确实很多时，二选一——(a) 在文件头加"类别目录"，AI 按目录只读相关类别段；(b) 按 `类别` 拆成 `过程文件/经验记忆/<类别>.md` + 一个 `经验记忆-index.md` 总索引（AI 先读索引，按需读单类别文件）。**条目不多时不必启用**，避免过度设计。
