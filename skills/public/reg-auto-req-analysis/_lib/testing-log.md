# 测试日志规范

仅适用于有 TFS 需求号（工作项）的测试流程：围绕某工作项的单测、计划校验、工作流 dry-run / execute、TFS 回读验证和回归测试。无工作项的纯单测、临时校验一律不记录。所有记录追加到仓库根目录 `过程文件/测试日志.md`；该文件为本机运行审计，不上传 TFS、不提交 Git、不覆盖历史。

## 记录规则

1. 每个 TFS 需求号（工作项）流程在其实际执行测试或验证后立即追加一条；成功、失败、跳过和因环境阻断都要记录。
2. 工作项流程的一条记录覆盖同一 `work_item_id + run_id` 的质控、分析及回读验证；重跑使用新条目，不修改旧条目。
3. 菜单清单与知识图谱必须同时说明“已起作用的范围”与“未证明的边界”；待确认信息不得省略。
4. 分析者描述只记录业务内容、菜单路径和操作路径；仓库、类、接口、Mapper、表字段等技术定位写入“知识图谱作用”或“待确认信息”。
5. 调用入参中的 `human_feedback` 与 `additional_info` 必须写入“用户手动反馈”，保留 `question_id`、`question`、`answer` 和额外说明原文；无论首轮、重跑或重分析诊断是否触发都要记录。两者均未传或均为空时写“无”。只记录这两个反馈字段，不记录 `tfs_pat` 等连接参数或其它请求字段。
6. 本轮最后一条记录必须写“经验记忆处理”，取值为 `APPENDED / DEDUP_NOOP / NOT_APPLICABLE / FAILED`，并附 `经验处理结果_<id>_<run_id>.json` 路径；缺失或未调用按 `FAILED` 记录。该状态仅标记副记录收尾，不改变 TFS 终局。

## 追加模板

```md
## <测试时间> · <测试类型> · <需求号或不适用>

- 记录 ID：<唯一标识>
- 执行窗口：<开始时间> ～ <结束时间>
- 执行模式：<单测 / validate / dry-run / execute / 回读验证 / 回归>
- 需求号：<工作项 ID 或不适用>
- 标题：<工作项标题或测试对象>
- 运行标识：<run_id 或不适用>
- 版本与状态：<执行前后 rev / TFS 状态，或不适用>
- 质控结果：<SKIP-ANALYSIS / PASS / NEED-INFO / NEED-REVIEW / 不适用>
- 是否 PASS：<是 / 否 / 不适用，并说明阶段>
- 标签：<执行前后标签或不适用>
- 菜单清单作用：<定位结果、用途与不能证明的内容>
- 知识图谱作用：<已证实事实、候选/未确认和边界>
- 待确认信息：<业务或技术待确认项；无则写“无”>
- 用户手动反馈：<有值时写规范化 JSON：{"human_feedback":[{"question_id":"...","question":"...","answer":"..."}],"additional_info":"..."}；两者均空写“无”>
- 经验记忆处理：<APPENDED / DEDUP_NOOP / NOT_APPLICABLE / FAILED；结果=过程文件/<id>/<run_id>/经验处理结果_<id>_<run_id>.json；原因=<简述>>
- 分析者描述：<业务描述、菜单路径、操作路径或不适用>
- 测试项与结果：<命令/验证点及通过、失败、跳过或阻断结果>
- 产物与审计：<计划、方案、审计文件或不适用>
- 异常与改进：<异常、重试、经验或无>
```

“用户手动反馈”中的字符串值必须逐字复制调用入参，换行、引号和反斜杠按 JSON 转义，不能只写摘要、诊断类别或“已处理”。缺失的反馈键按空数组 `[]` / 空字符串 `""` 归一化，保证每条有反馈的记录都可直接看出 A 通道回答和 B 通道补充。
